# 猫鼠游戏总体产品规划与重构建议

日期：2026-10-08。供项目负责人决定下一轮投入与版本范围。本文是基于现有项目的重构提案，未将新规则视为已经实现或已经经过用户验证。

建议继续做这个方向，在现有仓库上重建核心体验。产品定位应收敛为“帮助一个组织者，让一群熟人在指定场地快速开始并公平完成一场实景追逐游戏”。先服务组织者带队的小型活动，再考虑面向陌生人的活动平台。下一版的主要价值是容易组局、看得懂、裁决可信、愿意再来一局。

相关报告：[游戏规则与缺陷审计](02-非对称对抗与游戏产品报告.md)、[技术架构与实施路线](03-技术架构与实施报告.md)。原始基线：[PROJECT_PLAN.md](../../PROJECT_PLAN.md)。

UI 评价基于现有 WXML、WXSS 和交互代码，尚未进行微信真机截图评审。平台能力来自官方公开材料；真实市场需求、服务器压测与玩家留存仍需试点验证。

## 2 产品定位和需求假设

### 2.1 优先服务的用户

优先场景：一名社团负责人、朋友聚会发起人或活动领队，带领 6–12 名参与者，在经过确认的校园活动区、公园或场地内玩若干短局。第一批测试优先选择成年人熟人组局，便于快速发现规则和操作问题；这不是断言现有用户就是这一群体。

组织者要解决的是邀请、讲规则、分组、检查设备、处理争议、再开一局。玩家要解决的是快速进房、知道自己该做什么、理解位置情报、完成抓捕或躲避、知道为何输赢。

当前需求判断是有合理场景支撑的产品假设，尚无订单、访谈或使用数据证明市场规模。真正需要验证的是：用户愿不愿意在第二次活动继续使用；组织者是否明显减少了讲解和裁判负担。

### 2.2 核心价值和边界

保留实景移动、猫鼠阵营、地图情报和近距离确认。把“手机辅助线下互动”作为设计原则，避免让用户的大部分时间消耗在地图商店、答题或弹窗里。

首版不做陌生人匹配、城市级开放地图、直播、语音房、复杂养成和付费战斗优势。历史上的答题系统以后可以服务定向寻宝模式，但它与追逐时的注意力需求不同，不应为了复用代码而放回主玩法。

## 3 功能全景与统一取舍

阶段定义：A 为下一版受控试点必须具备；B 为试点证明需求后增加；C 为远期独立验证。A 不是“全部同时开发”，实施顺序见技术报告。

| 能力域 | 现有内容 | 下一版统一规划 | 阶段 |
| --- | --- | --- | --- |
| 身份 | 昵称、本地 playerId、模拟登录 | 真实会话、服务端成员身份；昵称只是显示名 | A |
| 创建与邀请 | 4 位房号、分享 | 唯一邀请编码、人数与模式预设、失效反馈 | A |
| 等待房间 | 玩家列表、设置、开始 | 准备状态、定位质量、场地确认、角色分配预告 | A |
| 场地 | 一个没有执行边界的范围数值 | 组织者确认区域、集合点、明确可活动范围 | A |
| 规则 | 多个可调数字，部分无效 | 一套标准短局预设，开局后锁定 rulesVersion | A |
| 对抗 | 猫追鼠、超时与全抓完判定 | 可验证的情报差、短局捕获目标、提前躲藏期 | A |
| 地图 | 全员标记、视野圈、多层浮窗 | 按身份授权的位置与情报；突出时效和不确定性 | A |
| 抓捕 | 静态二维码、10 米 GPS 检查 | 停下展示动态码、扫码确认、争议处理 | A |
| 淘汰 | 被抓后观战 | 明确退出战斗、隐藏实时敌方位置、下一局倒计时 | A |
| 断线 | 部分 rejoin 接口、无完整状态机 | 短暂重连、位置失效、异常暂停、取消对局 | A |
| 组织者控制 | 任意人都能调用结束 | 组织者暂停、取消、纠错裁决；留下原因 | A |
| 结算 | 系统弹窗、胜方字段缺失 | 独立结果视图、有效/取消区分、捕获记录、再来一局 | A |
| 定位停止 | 主要在页面卸载时停止 | 对局结束、退出、会话失效时统一停止 | A |
| 隐身与积分 | 猫 20 分、鼠 0 分、唯一道具 15 分 | 从首轮试点移除商店和经济；之后单独试一次性鼠方情报技能 | B |
| 任务和问答 | 有代码但默认关闭 | 归入独立的定向活动实验，不混入标准追逐 | C |
| 鹰眼、金身、轰炸 | 前端保留大量逻辑，后端不完整 | 隔离实验代码，不恢复为核心功能 | C |
| 历史 | 内存查询，与登录身份不贯通 | A 存本局结果；B 做我的近期活动与活动复盘 | A/B |
| 个人中心 | 登录页原型 | 最小资料和设置；不先做等级、勋章、社交主页 | B |
| 排行与分享 | 记分板原型 | 先分享本场结果；长期跨场排行需要防作弊与规则一致性 | B/C |
| 活动管理 | 尚无完整能力 | 活动模板、批量邀请、固定组织者和场地管理 | B |
| 经营 | 无支付闭环 | 验证组织者愿付费后做场次服务或组织工具，不卖胜率 | B |
| 多端 | 微信端原型 | 共用服务端规则；微信与 App 的定位能力分别验收 | A/B |

紧急退出和活动取消属于真实对局闭环，不应等社交举报系统建好才做。单纯的个人退出与结束整场必须是两个动作。

## 4 下一版用户旅程

### 4.1 组织者

创建活动 → 选择一个标准玩法和人数 → 确认场地及集合点 → 分享邀请 → 查看准备与定位状态 → 开始躲藏阶段 → 开始追逐 → 必要时暂停或裁决 → 结算 → 保留房间、轮换猫玩家再开一局。

默认设置应可直接使用。高级参数收起，并且只允许修改已经实现、可解释、已在规则版本中登记的选项。不能继续出现“保存成功但实际不生效”的选项。

### 4.2 玩家

打开邀请 → 填昵称并建立身份 → 读一屏规则 → 授权定位并测试 → 准备 → 看阵营说明 → 游戏中围绕一个主动作操作 → 完成抓捕/被捕 → 看结果或等待下一局。

拒绝定位应停留在准备流程，说明怎么恢复；不得在地图上显示为“已准备”再让用户自行发现玩不了。相机权限只在准备测试或首次抓捕时按需请求。

### 4.3 异常体验

| 情况 | 用户应看到的内容 | 产品处理 |
| --- | --- | --- |
| GPS 不准 | “定位偏差较大，等待更新”，显示更新时间 | 不把不可信坐标显示为实时精确点 |
| 短暂断网 | “正在重连，已断开 X 秒” | 自动恢复身份；不立即判负 |
| 断线过久 | “本局已暂停，请联系组织者” | 走统一暂停/取消规则 |
| 扫码过期 | “请对方刷新二维码后重试” | 不显示泛化的“操作失败” |
| 抓捕存在争议 | “请停止移动，由组织者确认” | 记录争议，不能抢夺手机强行扫码 |
| 被捕 | “本局已被捕，距离本轮结束还有 X” | 移除战斗按钮，不泄露实时战况位置 |
| 服务器恢复 | “正在恢复本局，请重新定位” | 服务端暂停状态下收集有效位置 |
| 主动取消 | “本局取消，不计胜负” | 不能由取消者选择获胜阵营 |

## 5 UI 重做方案

### 5.1 现有问题的根源

首页使用紫色渐变与大号 emoji，房间是深色卡片，地图同时出现多组高饱和按钮、记分板、角色说明、常亮提示、视野条和弹窗，视觉语言不统一。更重要的是，常驻信息没有按玩家决策顺序组织：用户先看见商店、分数和多种实验特效，却很难迅速回答“我现在该追谁、躲谁、按哪里”。

布局还有具体实现风险：地图页读取的状态栏和胶囊尺寸是 px，部分动态 top 却直接作为 rpx 使用；实际重叠程度需要真机验证。地图 marker 的全员常显 callout、默认展开的计分板会增加遮挡。上述问题不是只改一个配色能解决的。

### 5.2 统一视觉和交互方向

建议采用明亮、清晰的户外活动界面，底图为主，浅色实心卡片承载文字；猫用暖橙、鼠用青蓝，所有阵营同时使用文字和形状区分。emoji 只用于轻量表情，不再承担全部功能图标。先做统一间距、字体、按钮、提示条和弹窗，再做品牌插画。

地图页默认只保留三组信息：顶部阵营和目标、剩余时间；中间授权可见的地图；底部主动作和网络/定位状态。名单、规则和战况放到抽屉，暂停和退出放到明确的菜单。观战者、猫、鼠有各自的操作面板。

| 界面 | 主要任务 | 主按钮 | 可收起内容 |
| --- | --- | --- | --- |
| 首页 | 进入活动 | 加入活动；次级创建活动 | 玩法介绍、历史 |
| 创建流程 | 确认场地、规则、人数 | 创建并邀请 | 高级配置 |
| 等待房间 | 看谁准备好了 | 我已准备；组织者开始 | 规则详情 |
| 猫的地图 | 读情报、追踪、确认抓捕 | 扫码确认抓捕 | 队伍、事件、帮助 |
| 鼠的地图 | 看危险与生存目标 | 展示抓捕码 | 队伍、事件、帮助 |
| 被捕视图 | 理解自身状态并等下一局 | 回到集合点说明 | 本轮公开统计 |
| 结算 | 理解结果并复玩 | 再来一局 | 抓捕明细 |

界面数量由旅程决定，不再机械坚持“只能 4 页”。部分视图可做同一页面内的状态。先出首页、等待房间、猫/鼠地图、结算五类关键稿，并一起检查权限拒绝、定位失效、被捕和暂停状态，随后才扩展。

验收建议：首次使用者无需口头教学，30 秒内找到加入入口；规则阅读后能说出胜负条件；地图主动作一眼可见；常用触控区域以至少 44 个逻辑像素为设计目标；小屏和大字体不遮挡按钮；亮光场景能分辨角色及失效位置。以上是设计目标，必须通过真机任务测试确认。

## 6 分发渠道与多端策略

产品形态与获客渠道分开考虑。微信小程序是承载产品的方式；社团群、领队、活动组织者、短视频和线下二维码才是获得用户的入口。

| 形态 | 推荐职责 | 主要成本或限制 | 顺序 |
| --- | --- | --- | --- |
| 微信小程序 | 熟人邀请、短局验证；满足能力时可承载游戏 | 后台定位能力必须核验，当前版本只有前台定位 | 默认先做可玩闭环 |
| Android App | 持续活动、锁屏场景的主游戏端候选 | 安装转化、权限和机型适配 | 提前做定位样机，按场测决定正式开发 |
| iOS App | 与 Android 共用规则的正式移动端候选 | 定位生命周期、分发和审核准备 | 与 Android 做同等能力验证，不忽略 iPhone 参与者 |
| 抖音小程序 | 已经有内容转化后再验证的入口 | 再维护一套平台能力、分享与审核适配 | 后置 |
| H5 | 介绍、邀请说明、报名和结果分享 | 本轮不承担主要对局定位体验 | 按需要补充 |

默认执行路线：微信完成一轮短局；同时用极小的 Android/iOS 定位样机验证锁屏、切后台、弱网恢复和电量。这里的“同时”是工作计划中可交错安排的验证，不要求同时维护三个完整产品。

如果实测表明用户必须锁屏奔跑，而该微信账号无法获得所需定位能力，就将 App 提前为主游戏端，微信保留邀请和活动入口。混合客户端对战只有在位置质量、情报节奏、规则版本一致时才开放，避免 App 玩家与小程序玩家出现系统性优势。

微信后台定位公开文档说明了接口声明、用户授权和特定类目开通要求，但不构成本项目获批承诺。以实际小程序账号后台为准。[腾讯位置服务接口说明](https://github.com/TencentLBS/tencentmap-miniprogram-skill/blob/main/references/wx_location_api/wx.startLocationUpdateBackground.md)

Android 普通后台定位会受系统频率限制，需验证合适的定位前台服务和权限；iOS 需配置 Core Location 的后台能力并处理会话生命周期。做成 App 不等于自动获得稳定后台定位。[Android 官方说明](https://developer.android.com/about/versions/oreo/background-location-limits) · [Apple 官方说明](https://developer.apple.com/documentation/corelocation/cllocationmanager/allowsbackgroundlocationupdates)

### 6.1 第一批用户怎么来

建议先找 3 位能实际带队的组织者，每人约一场，提供可复用邀请文案、场地选择说明、一屏规则和活动后反馈。首轮以观察组局耗时、争议和复玩为目的。短视频内容展示真实活动过程和结果，用于吸引下一位组织者；不先投入泛流量广告。

潜在经营路径是组织工具、场次服务或团建方案。现阶段不冻结收费价、营收预期或付费率，也不把“用户觉得有趣”直接当成“愿意付费”。

## 7 验证指标和产品门槛

以下均为建议门槛，不是已有业绩。试点先排查基本可用性，不能用很小的样本宣称市场或平衡性成立。

| 指标 | 口径 | 初期目标 |
| --- | --- | --- |
| 成功开局率 | 达到预设人数的房间中，进入正式追逐的占比 | ≥90% |
| 开局准备耗时 | 最后一名计划参与者到场至进入躲藏阶段 | 中位数 ≤3 分钟 |
| 正常完成率 | 有正常终局且无技术取消的对局 / 已开始对局 | ≥95%，逐局核对 |
| 当场复玩率 | 有条件继续活动的组中，实际再开一局的占比 | 首先观察，探索目标 ≥60% |
| 两周组织者复办 | 有再次活动机会的组织者中，实际复办者 | 记录事实，不以口头意愿替代 |
| 抓捕争议率 | 被组织者介入的抓捕 / 全部抓捕尝试 | 逐项定位原因，探索目标 <5% |
| 首次被捕后的等待 | 被捕至本轮终局的时长 | 中位数目标 ≤2 分钟；持续超标就改局长/淘汰机制 |

活动数据至少包括房间、规则版本、人数、场地类型、阶段时间、正常或异常结束原因、客户端类型。业务指标不需要保存整条精确移动轨迹。

## 8 推进顺序

1. 先定标准玩法、抓捕规则、位置可见规则和断线处置，形成可供领队执行的一页说明。
2. 做五类关键 UI 与异常状态稿，邀请 3–5 人完成无口头引导的任务测试。
3. 实现服务端可信闭环和新的最小前端；同步做移动端定位可行性样机。
4. 用 6–12 人开展受控测试，先解决抓捕争议和定位失效，再调人数、情报周期、时长。
5. 通过验证后决定微信主端还是 App 主端，再投入长期历史、活动模板和商业功能。

重构优先级是裁决可信、对局好玩、操作清晰，三者需要相互验证。UI 工作可以从现在开始，但上线版不能只替换皮肤而保留可任意改结果的接口。

## 9 对旧冻结决策的修订提案

| 原决策 | 本次建议 | 原因 |
| --- | --- | --- |
| D-001 微信固定首发 | 保留微信验证入口；主游戏端由后台定位验证决定 | 用户具备多端能力，核心体验可能需要锁屏 |
| D-002 固定四页 | 改成围绕完整旅程安排页面 | 准备、异常与结算需要明确承载 |
| D-003 固定前台定位 | 仅作为小程序试点限制；App 另做可行性验证 | 不把历史限制当成长久产品目标 |
| D-005 固定 10 米 | 改成动态码为主、位置为辅助和争议校验 | GPS 的不确定性需在场地内验证 |
| 隐身与积分默认保留 | 首轮去掉经济系统，技能独立实验 | 鼠无收入、效果失效，且妨碍评价基础玩法 |
| D-007 REST 轮询 | 目标为增量实时同步加单一降级路径 | 5M 带宽和全量数据泄露要求重做协议 |
| D-010 App 必须很晚才启动 | 提前验证平台能力，正式产品仍按阶段实施 | 避免后期才发现首发平台不满足核心体验 |

本表登记的是提案；旧文件仍可追溯。实施前应将被采纳的部分写入新的规则和技术决策版本。

## 10 仍需通过事实确定的事情

第一批活动的组织者、场地和真实人数；是否必须锁屏持续游戏；现有 AppID、主体与定位接口权限；服务器操作系统、所在地、可用内存和实际网络质量；是否需要未成年人场景；用户愿意支付的具体价值。这些事项影响排期和渠道，但不妨碍先完成规则修订、可信后端及关键 UI 原型。

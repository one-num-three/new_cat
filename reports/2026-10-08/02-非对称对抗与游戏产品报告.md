# 猫鼠游戏非对称对抗与缺陷审计

日期：2026-10-08。结论：猫追鼠的方向可以成立，但当前版本尚不具备可信、完整的非对称对抗。角色标签不同，真实生效的信息优势、行动代价和反制机会却没有形成闭环。先修复规则执行错误，再用一套短局规则测试乐趣与平衡，不能从旧版输赢判断哪一方应当加强。

本文分为已验证缺陷、设计分析和下一版规则提案。玩法数值是试点起点，不是经过胜率统计的最终参数。配套：[总体产品报告](01-总体产品规划报告.md)、[技术报告](03-技术架构与实施报告.md)。

## 1 当前究竟在玩什么

后端默认 1 猫、5 鼠、600 秒，开始后随机分配；实际人数不必达到配置值。猫需要抓完所有实际分配的老鼠，超时仍有老鼠则鼠队获胜。被捕老鼠标记为 `isCaught`，不转化为猫，可继续看地图。现实中的移动速度由玩家体能决定。

客户端显示猫视野比鼠大 30%，但服务端不按视野过滤，地图也没有按距离过滤 marker；因此“猫有更大有效视野”的规则实际没有成立。所谓揭秘时间只被存储，未执行阵营隐藏。活动范围只有数值，没有中心、边界判定或出界处置。

猫初始 20 分，鼠 0 分，唯一启用道具隐身花费 15 分。任务关闭后鼠没有正常积分来源；抓人也不加积分。商店对双方可见，但鼠无法购买，猫的购买状态又不能持久保存。

核心实现证据：[后端角色分配](../../cat-mouse-server/server.js#L264)、[状态返回](../../cat-mouse-server/server.js#L367)、[抓捕](../../cat-mouse-server/server.js#L514)、[前端视野圈](../../pages/map/map.js#L964)。链接中的行号对应本次工作区，后续修改可能漂移。

## 2 为什么当前很难称为平衡的非对称对抗

| 维度 | 应产生的决策 | 当前实际 | 后果 |
| --- | --- | --- | --- |
| 信息 | 猫搜索线索、鼠选择路线与躲藏时机 | 双方能获得全部有效坐标和角色 | 容易退化为体能追逐，信息策略很弱 |
| 时间 | 猫主动推进，鼠有生存压力 | 鼠只需等待；无集合或撤离阶段 | 不动、远离场地可能成为占优策略 |
| 空间 | 通过地形和有限场地周旋 | mapRange 不执行 | 猫可能永远追不上远离场地的人 |
| 人数 | 多猫协作、多人鼠分散风险 | 默认一猫对五鼠且必须全捕获 | 单猫压力大，最后一鼠拖延收益很高 |
| 资源 | 技能制造主动权交换 | 鼠没分、唯一道具状态不保存 | 资源系统不能提供有效反制 |
| 淘汰 | 被捕后也有明确体验 | 长时间无操作且能看全图 | 等待无聊，还可能向队友报点 |
| 抓捕 | 到达真实接触后完成公正确认 | 依赖鼠配合展示手机，后台仅接收 ID | 现实争议与技术作弊叠加 |
| 中断 | 断线不应变成隐身或获胜工具 | 无完整失联判定，任意人可结束并选胜方 | 胜负不可信 |

“猫视野 +30%”不是完整的平衡方案。即使未来真的执行，圆形可见面积也约为原来的 1.3²＝1.69 倍，不能理解成只增加 30% 的搜索优势；实际还受建筑、路线和定位误差影响。

也不能把人数比例当成胜率。仅作数学直觉示例：假设每只鼠在一局被捕概率独立且均为 0.7，抓完 5 只的概率是 0.7⁵≈16.8%。现实不独立，这不是胜率预测；它说明“全捕获”条件会随着鼠人数增加而显著苛刻，必须与局长、场地和情报系统一起设计。

R05 的直接原因是 NodeCache 默认读取副本，而道具接口修改副本后没有 `roomCache.set`。不是概率性的前端不同步。[NodeCache 官方文档](https://node-cache.github.io/node-cache/)

## 4 静态检查发现的其他问题

这些发现来自代码路径，未逐项做真机或运行复现；不要与上表的运行证据混淆。

| 等级 | 问题 | 影响和处置 |
| --- | --- | --- |
| P0 | Socket.IO joinRoom 无会话/成员校验，位置广播不按接收者授权 | 修 REST 还不够，房间查询、重连、实时通道都必须同一可见性策略 |
| P1 | 四位房号随机生成、不检测冲突 | 新建房间可能覆盖旧房间；改为原子唯一分配，房号与内部 ID 分离 |
| P1 | catCount、mouseCount 等无整数范围验证，开局不匹配实际人数 | 可以出现无鼠、无角色玩家或非法配置；服务端按固定预设校验 |
| P1 | start 用随机 sort，且重复 start 不清空全部旧字段 | 分配不保证均匀，旧胜方/旧状态可能残留；使用可测试洗牌和独立对局对象 |
| P1 | 隐身广播判断为 invisible≤0，而保存的设计是到期时间戳 | 即使补写缓存，到期后也可能不恢复位置广播；统一 expiresAt>now |
| P1 | 无位置时跳过距离；零坐标被当缺失；无精度、过期和异常跳变检查 | 真坐标与伪造位置都可能误判；校验数值与时间，不把 GPS 当绝对裁判 |
| P1 | 前端轮询可重叠，超时请求会积压，较旧响应可以后到 | 可能回退状态；单飞请求和版本序号，重连拿完整授权快照 |
| P1 | 地图 unload 不调用 leave，后端无超时失联调度；leave 只标记但仍占位 | 实际失联不会自动变更；等待房间离开与对局断线分开处理 |
| P1 | 结束处理不立即停止定位，onShow 又可启动；没有 offLocationChange | 结束弹窗期间继续采集、重进可能积累监听；统一会话生命周期 |
| P1 | 二维码是可保存的 JSON，扫码允许相册；凭据没有服务端签发/消耗 | 截图、重放、伪造风险；动态 token、本地绘码、服务端原子消费 |
| P1 | QR 全局缓存没有以 matchId+memberId 明确失效 | 跨局或异步下载乱序时可能展示旧码；缓存按身份和到期时间管理 |
| P1 | 任务关闭但房间仍展示谜底设置；map.js 保留大量关闭功能 | 规则理解与配置失真；页面按同一 capabilities 和规则版本渲染 |
| P1 | 任务开启时答案下发、完成接口信任 reward/attempts，无真实答题、距离和过期验证 | 旧任务不能直接重新上线；重新设计服务端题目及奖励裁决 |
| P2 | 定位回调生成 markers 的路径不做隐身过滤，当前 map 绑定 allMarkers | 数据路径分叉，未来切换绑定会出现显隐回归；统一一条渲染路径，不夸大为已复现闪烁 |
| P2 | 房间 view 的“至少2人”与 JS/后端“至少1人”不同；revealTime=0 被 || 默认值覆盖 | 文案、规则与实际值需一致 |
| P2 | 结算用 navigateBack(delta:2)，但房间曾 redirectTo 地图；扫码最后一鼠也另行返回 | 路由栈和弹窗可能竞争；终局只由统一控制器导航 |
| P2 | winner 修复后，已被抓但团队获胜的鼠仍被文案称“成功存活” | 分开团队结果与个人生存状态 |
| P2 | 历史页按 userId 查，但玩家采用另一套本地 playerId；详情页不存在 | 先统一身份；不要恢复一个无法闭环的历史入口 |

活动边界、揭秘、真正视野过滤和掉线判胜不仅是参数未调好，而是没有完成对应机制。地图上的圆并不等于服务端规则。

## 5 下一版标准玩法提案

### 5.1 选择一种容易测试的模式

建议第一轮只实现“短局限时捕获”，每轮 6 分钟追逐，前置 30 秒躲藏。先不加答题、积分、购买或复活；玩家熟悉规则后，再决定是否需要目标点或救援模式。

| 参数 | 试点起始值 | 调整依据 |
| --- | --- | --- |
| 参与规模 | 产品目标 6–12 人；首次以 8 人为准 | 少于预设人数应重新选预设，不隐式改变阵营 |
| 猫数量 | 6–8 人配 2 猫，9–12 人配 3 猫 | 只开放这两个测试预设；4人1猫仅用于内部功能验收 |
| 胜利目标 | 捕获达到开局鼠人数的 ceil(60%)，猫立即胜 | 8人2猫6鼠需抓4只；技术退出不减少目标 |
| 鼠队胜利 | 截止时捕获数未达到目标 | 不要求所有鼠都生存，个人结果独立展示 |
| 轮次 | 先玩 2–3 轮，每轮重新抽选并优先轮换猫 | 不把猫鼠整队直接互换导致人数比例倒置 |
| 活动区 | 组织者实地确认的区域，试点可从约150–250米半径场地筛选 | 按实际可走路线和障碍调整，不能直接采用任意 GPS 圆覆盖道路 |
| 躲藏 | 30秒，猫停留集合点；服务端不允许抓捕、不发鼠情报 | 软件只能验证部分移动，领队仍要维持线下规则 |
| 淘汰 | 本轮出局，保留公开计数，不看敌方实时位置 | 若等待过长，先缩短轮次，再评估救援 |
| 技能 | 初期关闭 | 先判断基础追逐是否好玩，避免混淆因果 |

60% 捕获目标降低最后一鼠决定全局的极端性，但也可能使鼠方故意牺牲慢速队员。复盘应观察团队体验和个人参与时长，不能只追求阵营胜率接近 50%。

### 5.2 信息差应在服务端真实成立

试点方案：猫每 30 秒收到一次存活鼠的大致位置线索，位置量化到约 50 米网格；线索展示为区域和采样时间，不画成实时精确点。每次只刷新当前线索，旧线索显式过期。猫可以看队友有效位置。

鼠可以看到约 120 米内、定位仍有效的猫的位置提示，看不到远处猫；鼠队友可互见。玩家自己的位置始终可见。被捕者只看集合点、剩余时间和公开人数，不再提供战术观察视角。参与游戏的组织者也不能使用管理身份获得全图；如需现场裁判，应使用独立不参赛身份。

信息可见性矩阵：

| 接收者 | 自己 | 队友 | 对手 | 全员名册 |
| --- | --- | --- | --- | --- |
| 存活猫 | 当前有效位置 | 当前有效位置 | 每30秒一次的鼠方区域线索 | 名称、阵营、公开捕获状态，无隐藏坐标 |
| 存活鼠 | 当前有效位置 | 当前有效位置 | 120米内猫的有效位置提示 | 同左 |
| 被捕者 | 自己和集合点 | 无实时战术位置 | 无 | 仅公开状态 |
| 非参赛裁判 | 需另行授权 | 按裁判职责 | 按裁判职责 | 管理操作留痕 |
| 未入房者 | 无 | 无 | 无 | 不提供活动成员信息 |

显示近距猫位置也需要避免“刚进120米就精确刷新”形成剧烈抖动；可设进入120米、退出140米的滞回区间作为实验值。情报线索中不得附带原始坐标供客户端自行模糊。重复生成抖动坐标可能被平均还原，建议同一网格和时间窗口稳定输出。

双方同速时，拥有连续精确定位的一方很容易预判另一方。这个方案用周期线索换取猫的搜索机会，用近距预警给鼠转向机会；30秒、50米、120米都需现场验证，不保证预设已经平衡。

### 5.3 抓捕采用停下后确认

领队开局前说明：在能近距离确认对方身份并双方停下时，鼠展示当局动态码，猫扫码完成记录。不能要求奔跑时盯屏扫码，也不能允许玩家以拒绝展示手机获得永久免捕。

二维码由服务器签发，绑定 matchId、目标成员、nonce 和短有效期，初始可试15秒；客户端本地生成图像。展示即表示准备确认，成功扫码后不再追加多次弹窗确认。服务端校验猫身份、目标存活、局仍进行、凭据有效，并原子完成一次捕获。临时展示码或发起请求不能冻结对局、触发无敌或延长截止时间。

位置只做辅助校验。初始可试：双方最近位置不超过5秒、精度估计不大于25米、测得距离不大于50米，配合真实动态码接受；不满足则刷新定位或交组织者处理。50米不是允许隔空抓捕的玩法距离，真实近距接触仍是规则要求。这些阈值必须通过不同手机在场地内的并排和隔离距离测试校准。

动态码可以降低旧截图与伪造风险，不能阻止实时转发、同谋或 GPS 伪造。首阶段面向有组织者的熟人活动，不宣称达到高奖金赛事防作弊强度。争议由组织者写明原因进行捕获确认或否决，不能直接选整场赢家；终局提交后不覆盖原记录。

### 5.4 断线、出界、暂停和截止时间

| 事件 | 规则提案 |
| --- | --- |
| 定位超过5秒未更新 | 位置标记为过期；不再作为实时近距证据。已经合法发布的区域线索仍按原到期时间显示 |
| 超过15秒无有效会话心跳 | 显示重连状态、通知本人和组织者；不自动判捕获 |
| 超过30秒无有效位置或会话 | 全局进入异常暂停；停止抓捕、情报刷新和倒计时，要求原地等待 |
| 异常暂停 | 每局自动暂停总预算60秒；恢复需组织者确认全部参与者位置有效。预算耗尽仍无法恢复则取消，不计胜负 |
| 一名玩家重复掉线拖延 | 同样消耗全局暂停预算；长期异常只能取消或在新局排除，不能让单方无限获益 |
| 玩家主动退出正在进行的局 | 进入同一异常暂停流程；不把退出者自动算被抓，也不缩小胜利门槛 |
| 精确度差或单次越界 | 提醒并等待更多有效采样；不据一次漂移处罚 |
| 持续可信越界 | 初始规则为连续3次有效采样且跨度≥10秒，由组织者核实；进入暂停，返回后恢复或取消 |
| 安全紧急情况 | 任何玩家可发求助并立即暂停；反复触发交组织者处理，整场取消不计胜负 |
| 服务器重启 | 恢复为暂停，旧位置全部失效；收齐有效位置再恢复 |
| 截止与最后一次抓捕相撞 | 服务端提交裁决时 now≥endsAt，先判时间结束；只有此前提交的抓捕计入，不接受客户端回填时间 |
| 手动结束 | 组织者可取消，result=cancelled；不可把自己的阵营指定为赢家 |

暂停期间停止所有战斗计时，不能靠暂停让技能过期或捕获凭据长期续命。任何未消费抓捕凭据在暂停时作废，恢复后重签。若组织者同时参赛，出现利益冲突的争议优先取消该轮并重开；下一阶段再引入独立裁判。

## 6 如何测试平衡而不是凭感觉调参数

先排除 bug：匿名不能操纵、信息不泄露、重复抓捕只记一次、终局唯一、所有客户端展示同一结果。只有这些满足后，输赢数据才有比较意义。

第一批做 3 场活动，每场 2–3 轮，每轮记录人数、阵营、场地、规则版本和设备。首轮验证能否玩通，第二轮开始轮换猫；不要一轮同时改变人数、范围和技能。之后在相近场地累计更多轮次，再调整一个参数。

| 信号 | 可能原因 | 优先实验 |
| --- | --- | --- |
| 猫长期没有接触机会 | 线索太稀、场地太大、路径受阻 | 先缩小可活动场地或把线索周期30秒改为20秒 |
| 鼠很快集体被抓 | 线索太精确、出发期太短、鼠缺少路线 | 线索区域放宽、躲藏期延长；不先堆技能 |
| 总靠最后一名强者决定结果 | 全捕获或目标过高、场地不均 | 用捕获配额，检查体能分组与路线 |
| 玩家频繁盯屏 | 提示过多、地图信息依赖太强 | 减少常驻内容、情报到达轻提示，避免复杂任务 |
| 被捕者等待太长 | 局长过长或过早碰面 | 缩短回合、调整先藏期；之后才试救援 |
| 争议集中在10米阈值 | GPS 漂移而非操作问题 | 用停下展示动态码和位置质量校验，不反复微调一个距离 |
| 断线决定胜负 | 平台/网络能力不足 | 先改平台与恢复规则，不把问题计入角色强弱 |

建议记录猫队胜率、首捕时间、达到目标的时间、每名鼠参与时长、捕获争议比例、取消原因、实际再开局行为。团队胜利和个人出局分别展示，禁止用公开羞辱“最菜玩家”增加复玩压力。

猫队胜率35%–65%可作为早期排查信号，不能作为统计证明。20局样本在真实胜率约50%时，标准误差约11个百分点；场地和重复玩家还会降低独立性。先看明显失衡和体验问题，再追求精细数值。

## 7 后续技能和模式的进入条件

如果基础追逐稳定且鼠方需要一次主动决策，可试“本局一次屏蔽下一次区域情报”，不收费、不消耗积分。它只影响信息，不改变真实速度、碰撞或抓捕规则；效果必须由服务端计算，并向使用者说明何时生效。是否加入由场测决定。

救援模式能够减少等待，却会增加守尸、救援窗口与无限续局问题；感染模式能够让被抓者继续玩，却会改变阵营比例并产生滚雪球。它们应使用不同 modeId 和独立胜负条件，不作为标准模式里的一个临时开关。

答题寻宝可以发展成另一种活动产品；金身、轰炸、可叠加鹰眼等同时加入，会让线下规则难解释且增加判定争议。当前阶段优先完成一套可复玩的规则。

## 8 可直接交给开发的验收要求

1. 每局保存规则版本、初始阵营、捕获目标、场地和阶段截止时间，局中不可任意修改。
2. 所有指令从登录会话识别操作者，不能信任客户端提交的 role、owner、winner 或奖励。
3. REST 和实时通道使用同一可见性函数，任何旁路都拿不到不该知道的位置。
4. 两猫同时扫同一码只产生一次捕获；重复请求返回同一个裁决。
5. 时间到、最后一次捕获、退出、暂停并发时只能产生一个合法终局。
6. 断网、拒绝定位、相机返回、切后台、重新进房和服务器重启均有明确状态。
7. 已结束、已取消或离开的客户端停止采集位置，并移除监听和计时器。
8. 猫鼠各有一组真机用例，包含已捕获但团队获胜的结果文案和受限观战。
9. 技术正确性通过后再进行人群场测；自动化模拟不能代替真实追逐体验验证。
